## 基准结果（60 章 / 396 KB / 净化 12 条 + 标题 7 条）

| 场景 | 全书 (ms) | 窗口 (ms) | 分配量比 |
| --- | ---: | ---: | ---: |
| 净化全部章 | 37.4 | 7.5 | 6.0× |
| 章节切分（整本） | 17.7 | 16.3 | 3.2× |
| 文本改写（整本） | 0.1 | 0.0 | 6.6× |
| 端到端：点下一章 | 66.6 | 31.7 | 5.2× |
| **切换净化开关** | 57.5 | **6.1** | 6.8× |

**结论：值得优化** —— 最差场景（端到端）窗口方案仍快 **2.1×**，切换净化开关快 **9.4×**，
均超过 2.0× 判定阈值。

> 注：章节切分（17.7 vs 16.3）差距不大，因为切分是单遍扫描、正则命中即止；
> 收益主要来自**净化**（正则逐条应用）——这也正是"开关净化"这个交互的卡顿来源。

## 落地到实现的两处优化

1. **窗口式预取**（`BookSourceReadingSession`）
   - 原：只预取下一章（`PrefetchDistance = 1`）→ 连续翻页每次都要等网络往返（实测单章 100~400ms）。
   - 现：预取**前 2 + 后 4** 章（`PrefetchBefore/After`），并发上限 4。
   - 窗口有界：任意时刻只涉及 7 章量级，1663 章的书也不会全书处理。

2. **原文缓存 + 窗口内就地重算**（切换净化开关时）
   - **抓取阶段完全不净化**：`GetContentAsync` / `GetContentsIndexedAsync` 一律返回原文。
   - 会话缓存**未净化原文**（`_rawCache` LRU 8 章），净化在"读取 → 渲染之间"执行。
   - 切换开关 → `RepurifyWindow(当前章, 2, 4)` 只重算窗口内的章（原文在缓存，**零网络**）→ 重绘当前章。
   - 全书重算是 O(全书) 的正则替换（60 章 57.5ms，1663 章按比例约 1.6s），每次开关都等这么久不可接受。
   - 窗口外的章节在**读到时**按需重算（同样零网络）。

## 净化时机契约（关键）

> **抓取阶段一律不净化；净化统一在"读取 → 渲染之间"执行，受一级菜单总开关控制。**

| 阶段 | 是否净化 | 说明 |
| --- | --- | --- |
| 抓取（`GetContentAsync` / `GetContentsIndexedAsync`） | ❌ 否 | 只返回原文 |
| 整本下载落盘 | ❌ 否 | 落的是**原文**，所以下载后重开总开关依然生效 |
| 读取 → 渲染之间 | ✅ 是 | `BookSourceService.PurifyForDisplay`（总开关关闭时零开销直返） |

**为什么这样切**：源头存原文 → 总开关才**可逆**（关掉即刻还原，无需重抓网络）。
若引擎在抓取时就净化，缓存里是净化后文本，关掉总开关就无从还原。

实证（`dotnet run --project Uviewer/Sample/PerfBenchmark/tools -- proof`）：

```
① 抓取 GetContentAsync : <p>正文里有广告</p>   (长度 13)
   是否仍是原文       : 是（未净化）
② 渲染前 PurifyForDisplay: <p>正文里有</p>   (长度 11)
   是否已净化    : 是
③ 总开关关闭后 : <p>正文里有广告</p>   (长度 13)
   是否等于原文        : 是（开关生效）
→ 契约成立：抓取不净化，净化发生在读取→渲染之间，且受总开关控制。
```
